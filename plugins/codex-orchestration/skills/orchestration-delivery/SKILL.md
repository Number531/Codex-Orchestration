# Codex Orchestration bounded delivery

Use when the user requests a bounded implementation and no existing project workflow owns it. This skill provides a small cadence, not a second lifecycle for an active plan.

Read project instructions and relevant code. State the outcome, scope/non-goals, affected files, material risks, acceptance criteria and validation in one concise plan. Existing task authorization covers in-scope implementation; ask only for an unresolved material decision. Escalate to the project's persistent planning workflow when duration, risk or cross-system scope requires it.

Delegate only useful independent work. Use `explorer` for bounded source evidence and `worker` or `implementer` for disjoint edits. Supply exact owned paths, a self-contained question, constraints and expected evidence; spawn fresh with `fork_turns="none"` and no model/effort override. Preserve others' edits. If the guard denies a costly custom role, choose a suitable registered role or bring the actual policy change to the user; never disguise or bypass the denial.

Establish the smallest relevant baseline, implement the smallest coherent change, and run checks that exercise the changed behavior. Include regression tests for meaningful bugs. Use `auditor` when security, authorization, data integrity or architecture warrants adversarial review. Require a focused `verifier` pass for nontrivial delivery. Findings are evidence for the parent, not permission.

Remediate concrete failures within scope. Stop after two unsuccessful corrections of the same finding or earlier when evidence stops improving or a material decision is needed. Do not create extra plans or ledgers to continue the same work. Finish with what changed, validation, unresolved risks and exact remaining action. Follow project Git and remote authority; do not infer merge or publication approval.
